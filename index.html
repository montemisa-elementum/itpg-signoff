Eight applications, following the requirements workbook

This version takes the workbook literally: its eight application headings become eight Elementum Apps. Shared definitions become Elements, source-system data becomes Tables, and the 75 rows classified as “Task” become candidate AspectTask entities pending confirmation.

This is a testable interpretation—not a claim that every implementation choice is settled. It is deliberately close to the source so process owners can point to what is right, what is wrong, and what the missing process document changes.

1 · Proposed model

The workbook defines the process areas; Elementum entities implement them

The eight apps are the user-facing process boundaries. Supporting entities are chosen by behavior rather than by convenience: lifecycle work is an App, lightweight owned work is provisionally an AspectTask, reusable configuration is an Element, outside facts are Tables, and deterministic movement is Automation.

8 Apps

Process areas

Each workbook application owns a primary record and a lifecycle: Demand Request, Investment Decision, Capacity Plan, Initiative, Outcome Record, Dependency and Vendor Engagement, plus governance-model change.

75 candidates

AspectTasks

Lightweight supporting records listed as Task in the EDB: Cost Line, Milestone, Decision Condition, Assessment, Status Report and similar work.

Elements

Configuration

Products, objectives, demand types, gates, scores, authority thresholds, teams and other reference data that changes behavior without a redeploy.

Tables

Systems of record

Work items, actual cost, workforce, telemetry, contracts, invoices and vendor risk—read from the systems that already own them.

Automations are the arrows. They validate, route, create handoff records, start approvals, enforce gates, lock baselines, detect breaches and send notifications. They are not another record type.

4 · What “Task” means

A plausible platform mapping, with one real implementation gap

The EDB intentionally distinguishes Application from Task. `AspectTask` is an actual platform entity—not the same thing as a task inside an automation—and it matches many of these lightweight supporting records.

What AspectTask supports

Fields, records, status options, automations, layouts and relationships. It is intended for action items, subtasks, review items and workflow-oriented supporting work.

What it does not support

AspectTask has no stages and does not host AI agents. Complex multi-stage processes remain Apps; AI belongs on an App.

Current authoring reality

AspectTask is an available Elementum entity, but whether it is the intended destination for the EDB Task rows still needs confirmation. I found no current source evidence that AspectTask is scheduled for removal, so that assumption should not drive the design.

Do not automatically create all 75. “Task” is the workbook’s data classification, not proof that every row needs an AspectTask. Cost Line, Milestone and Decision Condition look like strong candidates. Composite Score may be a calculated field; Status History may be native; Governance Reporting Pack may be generated output. The process owner and product owner need to review the list by behavior.

5 · Application detail

What each app owns, consumes and hands off

Open an application to inspect its proposed lifecycle, requirement count, Task candidates copied from the EDB, shared data, external sources, handoffs and client configuration. Warnings are questions—not hidden decisions.

6 · Client inputs

What we need from the client, by application

The solution structure is reusable; the operating model is not ours to invent. Each process area needs named owners, policy decisions and source data before it can meet the workbook’s acceptance criteria.

Start data readiness early. The hard part is usually attribution: Portfolio ID on work items and finance records, product or initiative tags on cloud spend, outcome keys in telemetry, and stable vendor/contract references.
